## F01 — P1：执行期间修改资料后，旧任务仍把新资料标为已核对

位置：[App.tsx](../src/App.tsx)（第 39 行），prepare 的异步流程见同文件第 46～70 行，审核渲染见第 123～125 行。

`patch` 仅当任务已经 draft_ready 时重置状态；validating/filling/verifying 期间修改不会中断旧任务。prepare 闭包读取启动时的 product，结束时无 revision/runId 检查便设 draft_ready 和 dirty=false；Review 却读取最新 product。

复现：默认资料启动模拟填写，立即回到商品资料清空货号，再打开审核页；旧任务结束后仍显示回读一致并允许内部审核。修改价格、库存有同样风险。

建议：冻结执行快照并保存 job/runId；任何资料修改使该任务结果失效；异步提交结果前检查当前 runId 与 revision，审核必须针对该快照和独立 observation。重置资料也应取消旧异步流程。

## F02 — P1：清空价格或库存被隐式改成 0

位置：[App.tsx](../src/App.tsx)（第 102 行）。

数值输入直接 `Number(value)`。用户清空库存时 `Number('')` 为 0，随后非负整数校验通过；拼单价清空也会变为合法 0。设计明确区分“未知/未填”与“真实零库存”，这里会丢失该含义。

复现：按界面同一转换 `stock=Number('')` 调用 validateProduct，问题列表为空。

建议：输入态保留空字符串或 null，提交时显式转换；空值阻塞。金额用十进制解析后转整数分，真实 0 是否允许由已验证规则决定。

## F03 — P2：领域校验未覆盖已声明的数据不变量

位置：[domain.ts](../src/domain.ts)（第 115 行），尺寸检查见第 127～129 行，价格检查见第 121～122 行。

当前只检查 merchantSku 非空，不检查编码唯一；尺寸只判断某尺码行存在，不校验数值；variants 空数组也可通过；元单位浮点允许小于一分的金额。

直接调用现有函数，以下用例均返回 `[]`：两行 merchantSku 相同、衣长 -10、拼单价 129.001、variants=[]。这些不是仅等待真实平台才能发现的问题。

建议：补齐 D01/D02/D05/D06 的纯业务不变量和负例；复用一份执行输入验证器。当前运行代码没有调用仓库中的 JSON Schema，README“Schema 校验已实现”的表述需要收窄或补上接入。

## F04 — P2：定位报告 ready=true 不代表 R1 所要求的整页定位通过

位置：[pdd-verify-locators.mjs](../scripts/pdd-verify-locators.mjs)（第 78 行），字段循环见第 38～69 行。

ready 只看 config.fields 的 21 个标签祖先内是否各有一个 input/textarea/select，以及保存按钮数量。配置中的 control、placeholder、categoryBreadcrumb、variantMatrix 和 sizeLinkage 不参与验收，真实 SKU 行、图片用途、尺码表、物流也未检查。

复现：通过 jsdom 执行原始 evaluate 函数，构造 21 个同名 label+普通文本 input 和保存按钮；页面没有类目面包屑、SKU 表、尺码表和图片区，按现有 ready 表达式仍返回 true。

建议：短期将结论改为 basicFieldsReady 并明确未覆盖区域；R1 总通过必须包含控件类型/预期提示、类目范围、所有计划业务区域及唯一行键验证。未知/未实现区域不能默认为通过。

## F05 — P2：审核接口可以跳过准备和校验直接批准

位置：[mock-api.mjs](../scripts/mock-api.mjs)（第 92 行）。

`POST /reviews` 只校验 decision，不检查前置状态或输入/观察版本。创建一个无物流、无 offers 的 editing 刊登后直接 approved，实际返回 200 和 review_ready。

这违反 Mock API 应保留真实状态语义的约定；客户端可以在草稿尚未存在时获得审核通过状态。无需等数据库阶段才能约束。

建议：只允许已准备并校验通过的快照审核；否则 409。后续加入 snapshotHash/observedHash，returned 后再次 approved 也须重新准备。

## F06 — P2：现有模拟 E2E 只验证成功文案，不能验证填表和回读

位置：[mock-playwright.mjs](../scripts/mock-playwright.mjs)（第 11 行）、[App.tsx](../src/App.tsx)（第 58 行）、[mock-api.mjs](../scripts/mock-api.mjs)（第 90 行）。

前端使用定时器推进并生成成功日志，Mock API 将同一 listing 数据分别放进 expected 和 observed，differences 永远为空。Playwright 脚本仅点击启动、等待成功文案并截图，没有把 ProductPackage 填入独立商家表单，也没有读取其字段。

当前方案已将真实上传和故障注入后置，因此不要求现在补完整模拟商家系统；但不能据此将 SKU/尺寸/素材独立回读判定为通过。

建议：将现有测试命名为 UI 冒烟；后续 R2 用独立 ObservedForm 验证执行结果，并加入“实际库存被改错时必须产生差异”的负例。如果继续宣称模拟回读闭环，则需独立模拟表单状态和读取器。

## 已知后置项与其他风险（不作为当前阶段阻塞缺陷）

- 重复相同 Idempotency-Key 调 prepare 实际得到两个 jobId，并均成功。幂等/锁在 R5 待办中已有记录，但进入真实批量前必须实现，不能直接复用 Mock prepare。
- ProductPackage、前端 Product 与 Mock API 商品为三套数据形状，没有 compile/observe 转换实现。当前文档明确 D-202 尚未完成，应以统一执行输入贯通下一步，避免直接把前端浮点价格对象传给 Adapter。
- 前端没有新增/删除颜色尺码组合、真实图片导入或尺寸录入；loadProduct 还以三条默认 Variant 为基准合并，未来加入编辑/导入时会丢掉新增行或恢复删除行。当前仅适合作为固定夹具原型。
- 没有真实写入代码，发布门禁当前是独立函数及测试，尚未挂到未来所有写入路径。现阶段未发现自动点击平台发布的调用；这不证明未来执行器已受统一动作策略保护。
- 最新方案允许产品化后置；持久任务、店铺锁、输入确认、库存 TTL、媒体存储仍需在相应阶段落实。
